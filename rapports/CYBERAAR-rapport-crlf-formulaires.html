Injection de contenu arbitraire (CRLF) dans les e-mails de notification des formulaires publics

Programme : CyberAar — AarMe (bug bounty) · Actif visé : API formulaires — cyberaar.io/api/* (classe Standard)
Endpoints : POST https://cyberaar.io/api/contact et POST https://cyberaar.io/api/apply
Classe de la faille : CWE-93 — Injection CRLF · CVSS v4.0 : CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:P/S:X/VC:L/VI:L/VA:N/SC:N/SI:N/SA:N = 5,3 · Impact métier : 4/10 → score final CyberAar : √(5,3 × 4) = 4,6 (Moyenne)
Découverte : 22/10/2026 · Preuve : accusé de réception reçu avec le nom tronqué (capture §3)

1. Résumé

Les champs des formulaires publics de CyberAar ne sont pas nettoyés des caractères de fin de ligne (CR/LF) avant d'être utilisés dans les e-mails générés par la plateforme. La valeur fournie par l'attaquant est donc insérée brute dans le message, ce qui permet d'ajouter des lignes arbitraires au contenu de l'e-mail — y compris des en-têtes d'e-mail si le champ concerné atterrit dans un en-tête.

La preuve est directe et reproductible : le message d'accusé de réception renvoyé à l'expéditeur commence par « Bonjour, » sans le nom alors que le nom soumis contenait un retour à la ligne : le champ a été tronqué exactement à l'emplacement du \r\n injecté. Aucun nettoyage, aucun échappement, aucun refus.

Le risque principal n'est pas la plateforme elle-même mais la boîte de réception de l'équipe CyberAar : un attaquant peut introduire dans un message de confiance (envoyé depuis le site officiel) un faux bloc « De : … », une fausse signature, de faux liens, un faux avis de sécurité, ou une demande de désactivation de compte. C'est une voie de hameçonnage/impersonation à l'encontre du personnel de triage, dans un canal perçu comme interne. Le même défaut rend l'accusé de réception malformé (contenu tronqué).

3. Reproduction

3.1 Requête (une seule requête suffit)

curl -s -X POST https://cyberaar.io/api/contact \
  -H 'Content-Type: application/json' \
  -H 'Origin: https://cyberaar.io' \
  -d '{"name":"Test CyberAar\r\nBcc: bbtest4926@maxxspace.com",
       "email":"researcher+test@example-technique.org",
       "subject":"Test programme",
       "message":"Message de test - rapport de bug bounty."}'

Réponse : HTTP 200 {"success":true} — la charge est acceptée sans le moindre refus (alors que le champ email, lui, est validé : un CRLF dans email renvoie 400 {"error":"invalid_email"}).

3.2 Preuve de l'insertion brute

L'accusé de réception reçu par l'expéditeur (capture §5) commence par :

Bonjour,

Nous avons bien reçu votre message.

Notre équipe vous répondra dans les 24-48 heures ouvrées.

Le nom soumis était Test CyberAar\r\nBcc: … : le message affiche « Bonjour, » puis un retour à la ligne, et le reste de la charge a disparu du corps — il a été consommé comme un saut de ligne, exactement comme un saut de ligne injections dans un corps d'e-mail. La valeur n'est ni échappée, ni nettoyée, ni refusée : elle est insérée telle quelle.

3.3 Vérification côté en-têtes (à confirmer par l'équipe CyberAar)

Deux questions ne peuvent pas être tranchées depuis l'extérieur et sont explicitement laissées à la vérification interne (les étapes sont fournies) :

QuestionComment CyberAar peut le vérifier en 2 minutes
La charge atteint-elle un en-tête de l'e-mail (et non seulement le corps) ?Ouvrir l'e-mail reçu par l'équipe (contact@cyberaar.io) → « Afficher l'original » → rechercher une ligne d'en-tête supplémentaire (Bcc:, Content-Type:, Subject: replié…) ou un corps contenant une ligne From: / Reply-To: / Content-Type: text/html.
Le message est-il affiché dans un interface web de CyberAar (back-office, CRM, AarMe) ?Si oui : vérifier si le contenu est rendu en HTML → l'injection devient alors un XSS stocké dans l'interface de triage (actif Plateforme AarMe, classe Critique) et non plus une simple déformation d'e-mail.

Aucune donnée réelle n'a été modifiée, aucun envoi massif n'a été réalisé : la campagne a respecté la limite de débit de la plateforme (une requête par test, espacée) et les règles « pas d'attaque par déni de service ».

6. Correction recommandée

Nettoyer systematically les valeurs fournies par l'utilisateur avant toute construction de message (une seule fonction suffit) :

const clean = (v) => String(v ?? '').replace(/[\r\n]+/g, ' ').trim();

À appliquer sur tous les champs de tous les formulaires et à effectuer avant toute utilisation, y compris dans les en-têtes. Un contrôle de type « nom de personne » (lettres, espaces, tirets) sur les champs qui ne doivent contenir que du texte libre est un complément utile mais ne remplace pas le nettoyage.

9. Limites de la démonstration

  • La démonstration porte sur l'insertion brute de contenu dans l'e-mail (prouvée par l'accusé de réception tronqué). La propagation aux en-têtes et l'éventuel affichage dans une interface web relèvent d'une vérification interne : les étapes sont fournies au §3.3.
  • Aucun impact n'a été cherché sur des données réelles, aucun compte tiers n'a été visé, aucun envoi en masse n'a été réalisé.
  • Le compte de test utilisé est un compte de recherche créé par le chercheur, sur une adresse lui appartenant, avec son accord.
